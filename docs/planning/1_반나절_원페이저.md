## 해결하고픈 문제

### 어떤 유저의 문제를 해결할 것인가

- **비즈니스)**
  - **짐캐리** : 픽업 가능 숙소가 343개로 한정되어, 그 외의 여행자는 사용할 수 없다. 픽업 이용률이 정체된 외국인 FIT(9.7%)는 정보 장벽에 막혀 있고, 픽업 불가·마감 시 대안이 없어 그대로 이탈한다.
  - **부산교통공사** : 물품보관함·역사·승하차 등 시설 데이터를 보유하고 있으나 여행자 접점이 없어 활용되지 못한다.
- **고객)** 여행 마지막 날 캐리어와 함께 남겨진 사람들
  - ① 체크아웃 후 출발까지 반나절이 뜬 여행자
  - ② 한국어 정보 탐색이 어려운 외국인 FIT
  - ③ 짐을 든 채 이동해야 하는 여행자

### 어떤 문제를 해결할 것인가

**문제1) 마지막날, 어디를 갈지부터 정해지지 않는다**

- 니즈 : "반나절 남았는데, 짐 두고 다녀올 만한 데가 어디지?"
- 문제 : 관광지 정보와 짐 보관 정보가 완전히 분리되어 있다. 여행자는 관광 앱에서 목적지를 고르고, 다시 다른 채널에서 보관 수단을 찾아 스스로 동선을 조합해야 한다. 제공 데이터에도 관광지 POI는 없다.

**문제2) 내 동선에서 짐을 맡길 곳을 찾을 수 없다**

- 니즈 : "내가 갈 곳 근처에서 짐을 맡기고 빈손으로 다니고 싶다"
- 문제 : 짐캐리 픽업은 등록 숙소(343개)로 제한되고, 역내 물품보관함(71개 역)은 공공데이터로 흩어져 있어 '내 동선 기준' 검색이 불가능하다. 픽업 불가 여행자를 받아줄 대안 경로가 서비스 안에 없다.

**문제3) 캐리어를 언제 옮겨야 덜 고생인지 모른다**

- 니즈 : "붐비지 않을 때 짐을 옮기고 싶다"
- 문제 : 역별·시간대별 혼잡 정보가 여행자 관점으로 제공되지 않는다. 승하차 데이터(81,760행)는 존재하지만 시설관리 관점의 원자료라 여행자가 해석할 수 없다.

**문제4) 이용 방법을 물어볼 곳이 없다**

- 니즈 : "픽업은 어떻게 신청하지? 요금은? 마감은 언제까지?"
- 문제 : 픽업·무인 보관·배송 절차가 각 채널에 흩어져 있고 다국어 안내가 부족하다. 외국인 FIT의 이용률 정체(9.7%)는 곧 정보 접근의 문제다.

## 해결 방법

### 솔루션 : **가고 싶은 곳을 자연어로 말하면, LLM이 조회 도구를 호출해 동선 위 짐 보관 옵션·혼잡 시간·이용 방법까지 대화로 완결한다**

**해결1) 관광지 추천 — 대화의 진입점** — "마지막 날 어디가 좋아?"에 자체 큐레이션 POI(20~50개)로 답한다. **후보는 물품보관함 보유 71개 역 인근으로 한정**해, 추천한 곳이 곧 짐을 맡길 수 있는 곳이 되도록 설계한다. 관광 정보가 입력 동기가 되고, 그 자리에서 짐 문제로 자연스럽게 연결된다.

- 기대 효과 : 출발편·숙소를 몰라도 대화가 시작된다. 추천–보관 불일치가 구조적으로 발생하지 않음

**해결2) 동선 기반 보관소 추천 — 픽업 + 보관함 병렬 제시** — 숙소명으로 짐캐리 픽업 가능 여부(343개)를 판단하고, 동시에 관광지 인근 역의 특대형 보관함을 칸수·거리순으로 1~3개 제시한다. 사용자가 근거를 보고 직접 고른다.

- 기대 효과 : 픽업 불가가 이탈로 이어지지 않는 구조. 짐캐리에게는 343개 밖 수요까지 담는 접점 확보

**해결3) 과거 혼잡도 병기 — 옮길 시간의 근거** — 승하차 81,760행을 역×요일×시간대 등급(여유/보통/혼잡/심함)으로 사전 집계해 보관소 카드에 함께 표시한다: *"남포역은 주말 14~17시 혼잡했어요. 오전에 맡기는 걸 추천해요."*

- 기대 효과 : 혼잡 시간대 회피. 1단계는 과거 통계로 정직하게 제공하고, 2단계에서 예측 모델을 같은 자리에 꽂아 "통계 → 예측"으로 격상

**해결4) RAG 이용 방법 질의응답** — 픽업 방법·무인 보관·배송·요금·마감·FAQ를 문서화해 검색 도구로 등록한다. 검색된 근거로만 답하고, 문서에 없으면 "확인이 필요하다"고 답한다.

- 기대 효과 : 요금·마감 등 사실 정보의 환각 방지. 상담 없이 실행까지 연결

**해결5) 3개 언어 지원 — 한국어 · 일본어 · 영어** — 외국인 여행자가 자기 언어로 묻고 답을 받는다. 데이터·문서는 한국어 원본 하나만 유지하고 **LLM이 답변 시점에 사용자 언어로 조합**하므로, 언어별 화면·번역 테이블을 따로 만들지 않는다. 원본이 하나라 언어 간 정보 불일치도 생기지 않는다.

- 기대 효과 : 외국인 FIT의 언어 장벽 제거. 픽업 이용률 정체 구간(9.7%)의 직접 공략 수단



### 활용 데이터 & API


| 구분                 | 데이터                                                               | 역할                                       |
| ------------------ | ----------------------------------------------------------------- | ---------------------------------------- |
| **제공 데이터**         | 시간대별 승하차(81,760행, 2025) · 역사 정보(114역, 위경도) · (보조) E/L·상세위치        | 혼잡 등급 집계 / 관광지↔역 매핑·거리 조인 / 보관소 카드 접근 안내 |
| **외부 공공데이터**       | 부산교통공사 물품보관함 정보(71개 역, 크기별 칸수·요금·상세위치)                            | 역내 보관 후보 조회                              |
| **짐캐리 관련 (공개 정보)** | 픽업 가능 숙소 목록 + 이용 안내(픽업·무인보관·배송·요금·마감·FAQ) — 짐캐리 웹/앱 공개 정보를 수집·문서화 | 픽업 가능 판단 / RAG 지식베이스                     |
| **자체 구축**          | 관광지 POI 큐레이션 20~50개(명칭·위경도·인근 역·태그·소개), **보관함 보유 71개 역 인근으로 한정**  | 관광지 추천의 원천 — 제공 데이터 부재 영역을 직접 메움         |


> **POI(Point of Interest)** : 지도상의 관심 지점(관광지·식당·역 등). 'POI 큐레이션'은 관광지 목록을 직접 골라 데이터베이스로 만드는 작업을 뜻한다 — 제공 데이터에 관광지 정보가 없어 팀이 수작업으로 구축한다.
>
> **짐캐리 데이터** : 별도 협조 없이 **공개 정보만으로 자체 구축**해 서비스가 성립하도록 설계한다. 대회 중 공식 데이터(숙소 원본 리스트·주문 로그)를 받으면 같은 자리에 교체 투입해 정확도와 확장 기능(짐 도착 ETA 등)으로 이어간다.



### 제공 AI 기능

**LLM 오케스트레이터 (Function Calling)** — LLM은 답을 지어내지 않고, 등록된 조회 도구의 결과로만 답변한다.


| #   | 도구         | 입력 → 출력                            | 데이터 원천      |
| --- | ---------- | ---------------------------------- | ----------- |
| 1   | `관광지 추천`   | 취향/조건 → 인기 관광지·지역 목록 (보관함 보유 역 인근) | POI 큐레이션    |
| 2   | `보관소 조회`   | 관광지/루트 → 보관소 1~3개 (위치·크기별 칸수·요금)   | 보관함 71역     |
| 3   | `픽업 가능 판단` | 숙소명 → 짐캐리 픽업 가능 여부                 | 픽업 가능 숙소 목록 |
| 4   | `혼잡도 조회`   | 역·시간대 → 과거 혼잡 통계 (요일·시간별)          | 승하차 81,760행 |


- 후보 선정 로직(인근 역 탐색, 거리순 정렬, 특대형 칸수 필터)은 도구 내부의 **규칙 기반 코드**로 두어 결과의 재현성을 보장한다.
- LLM의 역할은 의도 파악 → 도구 선택·호출 → 결과를 근거와 함께 자연어로 조합하는 것까지로 한정한다.

**RAG 질의응답** — 이용 안내 문서를 주제 단위로 분할해 검색 도구로 등록, 근거 문서 조각을 표시하며 답한다.

**다국어 대화 (한국어·일본어·영어)** — 도구 조회 결과와 RAG 근거 문서는 한국어 원본 그대로 두고, LLM이 사용자 언어로 실시간 조합·전달한다. 언어별 번역 테이블을 관리하지 않으므로 데이터가 갱신돼도 3개 언어가 자동으로 최신 상태를 유지한다. 단, 역명·관광지명 등 고유명사와 요금·시간 표기는 원문 병기 규칙을 두어 오역을 차단한다.

## 기대 효과

- **사회적 가치** : 
  - ① 마지막 날 반나절을 '짐 고생'에서 관광·소비 시간으로 전환 
  - ② 한국어·일본어·영어 대화로 외국인 FIT의 언어 장벽을 해소해 이용률 정체 구간(9.7%) 공략 
  - ③ 시설관리용 공공데이터의 '여행자 관점' 재해석 — 관광지·보관함·혼잡을 하나의 대화로 통합 
  - ④ 짐 없는 이동은 곧 무장애 이동, 교통약자 동반 여행자에게 동일하게 유효
- **타 팀과의 차별점** : 
  - ① **통제된 LLM** — 자유 생성 챗봇이 아니라 도구 호출·문서 검색으로만 답하는 구조로 요금·칸수 등 사실 환각 차단 
  - ② **픽업 밖 수요를 담는 설계** — 343개 숙소 밖 사용자가 보관함 경로로 자연 전환, 이탈 방지가 기능이 아니라 구조 
  - ③ **외부 협조 없이 완결되는 데이터 설계** — 공개 정보와 자체 큐레이션만으로 서비스가 성립, 제공 데이터에 없는 진입점(관광지)까지 직접 구축 
  - ④ **정직한 단계 설계** — 1단계는 과거 통계로 제공하고 2단계에서 예측 모델로 격상하는, 과장 없는 로드맵
